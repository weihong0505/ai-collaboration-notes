# 可证伪的验收：怎么让 AI 的产出骗不了你

> 来源：作者 41 份项目复盘中与「验收标准 / 判定线 / 留失败数据」相关的条目。
> 核心命题：**如果验收标准可以被结果反过来修改，那它就不是标准。**

---

## 一、判定线必须在看到结果之前冻结

**做法**：跑检验前，先把判定阈值写进一个配置文件并提交入库（如 `frozen_config.json`），
之后无论结果好坏都不得回改。

某因子检验项目的判定线（检验前冻结）：

| 关卡 | 条件 |
|---|---|
| IC 关 | ICIR > 0.5 且 \|mean IC\| ≥ 0.02 且 signed NW-t ≥ max(3.0, Bonferroni(N'=4)) |
| 分层关 | 单调性检验 p < 0.05 且倒挂 ≤ 1 档且 Q5 > Q1 |
| 经济闸门 | 净多空年化 ≥ 4~8% 且夏普 ≥ 0.5 |

**结果**：4 个核心因子**全部未过闸门**。

**关键动作**：报告里专门写了一句 ——「**未做「选择性报告」**：四个因子全部如实报告，
包括 GPM 这种「几乎完美不显著」的结果（p = 0.8291）」。

> **规则**：先冻标准，再看结果。**在结果出来之后调整门槛，等于没有门槛。**

## 二、留失败数据，比展示成功数据更有说服力

| 做法 | 具体实例 |
|---|---|
| **不删不可复现的历史值** | 某基准表里一行写「189 ms（历史值，**现不可复现**）」—— 因为按新环境重跑会让进程段错误，同机同刻另一张图却正常。这行**留在表里并标注**，没删 |
| **保留被自己淘汰的因子** | 因子知识库里，动量与量比两个因子的页面记录的是**被淘汰的过程**（一个反向显著 signed NW-t = −3.63，一个不显著），不是用法 |
| **保留推翻自己的结论** | 回测报告单列一节「首版错误结论留档（备审计）」，写明根因与修正值 |
| **公开"不能说什么"** | 每个大项目都有一节「明确不能说什么」 |

某回测报告的「不能说什么」原文照抄：

> 1. 不能说「可实盘」—— 因子级证据链未满足
> 2. 不能说「时点精确」—— 实为 78 次不等间隔调仓，非严格月频
> 3. 不能忽视风格风险 —— 历史上有 **−32%** 的 36 月超额断点
> 4. 不能把分红修正后的绝对值当精确值 —— 该系数是硬编码常数，未经独立证实

> **规则**：**一个只展示成功数据的项目，读者无法判断作者有没有分辨能力。**

## 三、误判代价不对称时，往保守那边偏

分类/判定任务里，两边的错误代价往往不对等。

**实例**：判断一个代码仓库是"可部署应用"还是"开发库"——

- 误判为「库」→ **不可逆地错失一个项目**
- 误判为「应用」→ 后面还有评分、审查、人工三道门兜着

**策略**：**只在置信时判「库」**。强信号（有容器化配置）直接判应用；
库特征 ≥2 项才判库；其余一律落到 **`unknown` 第三态**。

**配套**：**规则必须用真实数据回测**。首版纯加权评分在 21 个真实项目上立刻暴露 2 处误判
（单体仓库的子包信号把某库判成了应用）。**单测的构造场景完全不够。**

> **规则**：先问「判错的代价哪边更大」，再定阈值往哪偏；并且一定要用真实数据回测规则。

## 四、架构保证要**分层**声称

这是作者认为最有价值的一次被审查纠偏。

**初版声称**：「入口层受控 ⇒ 判定正确」。
**审查把它拆开了，而且拆得对**：

> **「写入点受控」≠「判定正确」。**

入口层（让模型在结构上写不出终审结论）确实成立；但**判定正确性层当时并不成立** ——
事实源不唯一、依赖审查缺位、多许可证文件不扫描。

**补齐动作**（逐项落地）：许可证正文特征核验（不只信元数据字段）、多许可证逐份取最严、
依赖清单关键词扫描、冲突时以许可证文件为准而非 README 声明、解析失败时 fail-safe 为「未知」而不是猜一个。

> **规则**：声称一个安全属性时，**必须指明它覆盖哪一层**。
> 「X 不可能发生」这种话，要么给出机制，要么限定范围。

## 五、假绿测试比缺测试更危险

**实例**：一个名为「GPL 应被拦截」的测试，实际验证的是「**没有许可证文件 → 拦截**」这条分支。
它和一个真正测 GPL 拦截的测试**名字一样**，但它什么都没证明。

**危害**：它会让覆盖率好看、让回归"全绿"，从而**掩盖真实缺口**。

> **规则**：**测试的名字声称什么，就必须断言什么。**
> 定期抽查：这条测试如果删掉被测逻辑，它会红吗？

配套做法：修复缺陷时**先写能复现缺陷的红测试**，再改实现（TDD 先红后绿）；
修复后**跑全量回归**，不是只跑新增那几条。

## 六、开放集合上，词表法会结构性失效

**实例**：某内容合规审查最初用违禁词表实现。六轮迭代的真实轨迹：

| 轮次 | 换的说法 | 后果 |
|---|---|---|
| 1 | 绝对化用语 | 词表覆盖 |
| 2 | 「一键安装」 | 补词 |
| 3 | 「社群化官方暗示」 | 补词 |
| … | 每轮换一个新表述 | 词表永远落后一轮 |

**结论不是"词表还不够长"，而是「词表法在开放集合面前结构性失效」。**
最终把架构从"本地词表拦截"改成「生成 + 审查 + 按反馈重写」的闭环，实测 2 轮内收敛。

顺带修掉的三个真 bug：词边界匹配误伤（`Llama` 命中 `ollama`）、
全局字符串替换破坏语义、**模板自身被自己的词表拦下**。

> **规则**：如果一个防护机制的本质是"枚举所有坏情况"，它在开放集合上必然失效。
> **要改的是架构，不是词表。**

## 七、样本量不够时，结论要降级而不是加强

| 场景 | 处理 |
|---|---|
| 样本月数 < 60 | 所有结论**自动降级为「初步」** |
| 试点 101 只 → 全样本 5,179 只 | 发现某因子的 IC 在试点上是全样本的 **1/3.8** → 明确写「**试点样本的 IC 量级不可外推**」 |
| 参数显著性需要 2,328 个交易日（≈9.2 年）才能确认，而可用窗口只有几十天 | 直接写「这个回测**不能支持任何策略性结论**」 |

> **规则**：样本量不足不是"结果仅供参考"，而是**"不能下结论"**。
> 用最小 track record 要求（如 PSR/DSR 一类方法）算出"要多少样本才够"，再和实际样本比。

## 八、一份可复制的验收清单

- [ ] 判定阈值是否在**看到结果之前**就冻结并入库？
- [ ] 有没有一节明确写「**不能说什么**」？
- [ ] 失败/被淘汰/不可复现的结果，是否**留在报告里**而不是删掉？
- [ ] 有没有为了好看而做的**选择性报告**？（把所有受检对象列出来数一数）
- [ ] 分类任务的错误代价是否对称？不对称时阈值往保守偏了吗？
- [ ] 规则/阈值是否用**真实数据**回测过，而不是只过单测？
- [ ] 安全声称是否标明了**覆盖哪一层**？
- [ ] 抽查 2 个测试：删掉被测逻辑，它会红吗？（**假绿检测**）
- [ ] 防护机制是"枚举坏情况"还是"结构性保证"？前者在开放集合上会失效
- [ ] 样本量够吗？用最小 track record 要求算一遍

---

## 九、一句话总结

> 让 AI 的产出骗不了你，只需要三件事：
> **标准在结果之前冻结、失败数据留在报告里、安全声称标明覆盖哪一层。**
