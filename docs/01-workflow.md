# 工作流：一个人 + 多个 AI 代理，怎么把模糊需求变成可审计交付物

> 来源：作者 41 份项目复盘（约 44 万字符）中反复出现的流程模式。
> 本文描述的是**实际在跑**的流程，不是理想流程。

---

## 全景

```
① 钉目标  →  ② 写规格  →  ③ 并行取证  →  ④ 对抗性审查  →  ⑤ 交付 + 留痕  →  ⑥ 沉淀
   (一次问答)   (先评审规格)   (互不依赖的线并发)   (另起上下文)     (REVIEW.md + git)   (知识库)
                                    ↑                        │
                                    └────── 发现缺陷回炉 ──────┘
```

---

## ① 钉目标：一次问答，省掉整轮返工

**反面**：用户说「目前有 1800 的启动资金在股市中发展」。
这句话有 4 种可能解读：投资方案 / 模拟盘 / 量化基建 / 可行性判断。

**做法**：先问一次，钉死为「闲钱 + 学投资 + 要一份明天就能照着做的实盘方案」。

**收益**：避免按错方向做完 8 份交付物。
项目复盘里对这一步的评语是：**「若跳过这一步，整份方案会是空的。」**

> **规则**：目标里的每一个歧义词（"发展""优化""搞一下"）都是一个可能的返工点。
> **先钉死目标/范围（含不做什么）/约束/交付物/验收标准，再动手。**

---

## ② 写规格：先评审规格，再写代码

**做法**：动手前先写一份设计蓝图（spec），把范围、边界、状态机、验收标准写清楚；
**然后先评审这份 spec**，再写实现。

某项目的实证：spec v1.0 经过 **4 份独立对抗性评审**（合规法律 / 技术架构 / 平台实操 / 流程完整性），
得到 **90 条补漏点**，全部整合后重写为 v1.1。其中改掉的高危项包括：

- 把「某危险误判率为 0」从**统计声称**改成**架构保证**（让模型在结构上无法输出该结论）
- 把默认交付形态从「GUI 自动化」改成「内容导出 + 人工发布」（因为有自动化连续封号的实证）
- 定价与交付形态对齐（未上线的交付档位**禁止销售**）

> **规则**：**spec 的缺陷比代码的缺陷便宜一个数量级。** 评审要放在 spec 阶段，不是代码阶段。

---

## ③ 并行取证：互不依赖的线，同一条消息发出

**做法**：把任务拆成互不依赖的取证线，在**同一条消息里**同时派出去，而不是串行搜。

**实证收益**：某次三路并行（市场数据 / 规则费用 / 对抗审查）中，
规则线的一手发现（监管机构正在调研某费率的存废）**直接改变了整个方案的战略重心** ——
从原设想的方案 A 改为方案 B。**串行做的话，方案会按错前提设计完 8 份交付物。**

**配套约束**：

| 约束 | 原因 |
|---|---|
| 子代理不可再生子代理 | 会返回 `depth 2 exceeds maxDepth 1`。派活时要么不假设它能再分派，要么在任务书里写明「不可再分派，用并发抓取替代」 |
| 派活后必须盯**产出落盘** | 只盯"已启动"会漏掉静默失败（实测 4 个并行评审里 1 个首跑无产出、无说明） |
| **有状态、次序敏感的写操作不要并行** | 会踩锁和状态位。某次整库迁移是单会话串行做的，因为"删模型"和"迁目录"共享同一个活动资源 |

## ④ 对抗性审查

见 [`02-adversarial-review.md`](02-adversarial-review.md)。要点：

- 审查员**不接触**实现者的推理过程
- 被审版本先 commit 并**冻结**（否则审查结论失去锚点）
- 审查员也会错 —— 冲突时**回一手原文裁决**，不投票
- 分层：逐任务评审 + 全分支评审（跨任务语义不一致只有后者能抓）

## ⑤ 交付与留痕

### 5.1 一手证据先落盘，再写结论

**做法**：抓到的原始材料（官方公告、费率表、行情快照）先落到 `raw/` 目录，
结论必须能指回具体文件与条款。

**实证**：某次审查主张与作者判断冲突，裁决方式是取三份一手原文并写进 `raw/` 留档。

### 5.2 脚本与文档必须互相可对账

**做法**：计算脚本的输出、和独立核查报告的数字，**逐项比对到小数点后 4 位**。

**实证**：两处独立产出的同一笔费用结果 `10.3141 / 10.6282 / 10.1200` 逐位一致。
作者在比对过程中**发现自己的脚本漏了两项规费**（差异约 0.5%）。

> **规则**：**两套独立算出来的数字对不上，先怀疑自己。**
> 差异不一定要大到影响结论才算错 —— "用于精算的脚本不该有已知缺口"。

### 5.3 改动前先备份，改完必留痕

| 动作 | 做法 |
|---|---|
| 动手前 | 把要改的文件复制到 `backup/<时间戳>/`（备份目录走 `.gitignore`） |
| 每次改动 | git commit + 追加复盘条目 |
| 每次改动 | 同步更新对应文档（**漏了文档同步 = 任务没做完**） |

> 两者分工：**git 快照保证改错能退，backup 目录保证"改了什么"可查。**

### 5.4 复盘固定四问

每个项目维护一份 `REVIEW.md`，逐轮追加：

```
### YYYY-MM-DD HH:MM（时间已校准）
- 关联 commit：
- 做了什么：
- 关键决策：
- 教训 / 坑：
- 下一步：
```

**这条制度本身产出了本文档库** —— 41 份复盘、约 44 万字符，
全部是可检索、可举证的工程经验，而不是散落在聊天记录里的印象。

## ⑥ 沉淀：把一次性经验变成可复用纪律

**做法**：踩到的坑按「现象 → 根因 → 修法 → **可复用规则**」四段式写下来，
并按主题归到知识库的固定分类里。

**关键区别**：
- ❌ 「这次我遇到了 X」
- ✅ 「**遇到这类现象时，去看 Y**」—— 现象与根因之间要建立**可检索的映射**

**实证**：某次目录移动失败，逐文件试开独占句柄**全部可打开**，看起来没有锁。
真因是某进程的**当前工作目录**钉在该目录上，而系统不允许改名任何进程的 CWD 或其祖先目录。

> 由此得到的可复用规则：**「移动目录失败但文件都能独占打开时，别继续找文件锁，
> 去查谁的命令行/CWD 指向这个目录」。** —— 这条规则与"哪次事故"完全解耦，任何项目都能用。

## 七、一份可复制的工作流清单

**动手前**
- [ ] 目标/范围（含不做什么）/约束/交付物/验收标准，是否已钉死？
- [ ] 目标里每个歧义词是否都澄清了？
- [ ] 非平凡任务是否先有 spec，且 spec 经过独立评审？
- [ ] 要改的文件是否已备份？
- [ ] 互不依赖的取证线能否并行？

**执行中**
- [ ] 一手证据是否先落 `raw/`？
- [ ] 有状态、次序敏感的写操作是否保持了串行？
- [ ] 派出去的任务是否在盯产出落盘？

**收尾**
- [ ] 独立对抗性审查跑了吗？被审版本冻结了吗？
- [ ] 脚本与文档的数字对账了吗？
- [ ] 判定线是结果之前冻结的吗？
- [ ] 失败数据留下了吗？
- [ ] git commit + 复盘四问 + 对应文档同步，三件都做了吗？
- [ ] 新踩的坑是否沉淀成了"可复用规则"？

---

## 八、一句话总结

> 这套流程的全部价值，可以压缩成一句：
> **让每一步都留下能被别人（和未来的自己）检验的痕迹。**
