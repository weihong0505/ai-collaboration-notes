# 对抗性审查：怎么用 AI 找出自己的错，以及审查员自己错的时候

> 来源：作者 41 份项目复盘（约 44 万字符）中与「独立审查」相关的全部条目。
> 本文只收录**能迁移到别的项目**的规则，不收录只在单一项目成立的结论。

---

## 一、基本做法

每个非平凡任务都跑一轮**独立审查**：另起一个不带实现思路的上下文，只给被审对象，让它从攻击面出发找问题。

三条硬约束：

1. **审查员不看实现者的推理过程** —— 否则它会顺着你的思路走，变成复述而不是审查
2. **审查结论必须落到可复现的证据上** —— 能给出复现命令/文件行号，否则只是意见
3. **被审版本必须先入库并冻结** —— 见 §四，这条是踩出来的

## 二、审查确实能抓到致命缺陷（三个实证）

### 实证 1：一行索引对齐错误，让整个回测结论翻转

**现象**：某个成本敏感性分析报告出「2x 成本下主段超额转负（−1.81%）」，据此把一条验收判定为不满足。

**根因**：
```python
nav2.index = nav1.index[:len(nav2)]   # 应为后 N 个，写成了前 N 个
```
2x 净值序列被贴在基准的**前 116 个日期**上，整体早标一个月，窗口起点错到 2019-02-28，**丢掉了 2019 年 2 月的 +22.0%**。

**修法**：修正索引对齐，主段 2x 年化 6.688% → **9.441%**；四种独立口径复算全为正。

**可复用规则**：**成本/收益序列重采样后，必须断言首末索引与基准一致。** 一句话的断言，省掉一次结论翻转。

> 附带的做法：首版错误结论**没有删掉**，保留在报告里单列一节「首版错误结论留档（备审计）」，写明根因与修正值。
> 一个只展示修正后结果的报告，无法证明修正确实发生过。

---

### 实证 2：把用户输入直接拼进全文检索的 `MATCH` 短语，可被引号注入

**现象**：独立审查实测 `q = '"""'` 触发 `OperationalError: unterminated string`；
`q = 'xyz" OR "辆货车'` 可**逃逸引号、注入全文检索引擎的布尔算子**。

**根因**：查询串被直接拼进 `MATCH` 短语，没有做特殊字符处理。

**修法**：新增 `_fts_safe` 检测 —— 含 `" * - ( ) :` 或大写 `AND/OR/NOT/NEAR` 的查询走 `LIKE` 字面回退；
常规 ≥3 字查询仍走 `MATCH`（不回归）。按 TDD 先写红测试再修。

**可复用规则**：**任何"把用户输入拼进查询语言"的地方都要问一句：这个语言的元字符是什么。**

---

### 实证 3：审查发现的两个"沉默级联"问题

**现象 A —— 写失败后连接泄漏**：`insert_*` 系列没有 `try/finally`，写异常时 `conn.close()` 不执行，
且 traceback 帧持有 `conn` 引用，写锁常驻 → 后续所有写入报 `database is locked`，级联扩散。

**现象 B —— 参数为 0 导致死循环**：某窗口参数取 0 时，循环条件恒真且缓冲区永不缩减（DoS 级）。

**修法**：统一 `_write` 上下文管理器（成功 commit / 异常 rollback / finally close，异常仍上抛不吞）；
在入口处 fail-fast 校验参数 > 0。

**可复用规则**：**「写操作是否一定会释放资源」和「参数取边界值时循环还成立吗」应作为固定检查项。**

## 三、审查员也会错，而且错法有规律

这是本文最重要的一节。

某项目的独立审查报告 **842 行，找出 4 个真错误**，**同时提出 1 个它自己错了的主张**：

> **审查主张**：「深市不收过户费。」
> **处置**：没有投票、没有取"看起来更细"的一方，而是回一手原文取三份文件裁决：
> - 中国结算 2015-07-09 通知：「深市按照成交金额 **0.0255‰** 向买卖双方投资者分别收取」
> - 中国结算 2022-04-28 通知：沪深 A 股统一下调为 0.01‰ 双向收取
> - 中国结算某收费一览表（2025-06-30 更新）投资者业务项下**明列**「交易过户费 | A股 | 按成交金额的 0.01‰ 向买卖双方收取」
>
> **结论：该主张不成立，推理属「表种错配」** —— 用了一张**本不该包含该费用**的表，
> 去证明该费用不存在。裁决全程留档。

**由此得到三条规则：**

1. **独立审查的价值在于制造对账压力，不在于审查员一定对。**
   最终裁决必须回到一手原文。
2. **「看起来更具体」≠「更正确」。** 细节密度会造成可信度错觉 —— 引用了具体表格、具体条款，但用错了表。
3. **审查结论与你的判断冲突时，不要投票、不要取中间值，去取原文。**

## 四、一个必须记录的方法论失败：边审边改会让审查失去锚点

**事实**：审查员读到的被审文件是某一时刻的版本；但作者在审查进行期间（约 3 分钟内）
**并行把该文件改写并同步改了脚本**，且**被审版本从未入库、现已不在工作区**
（审查员用 `git cat-file --batch-all-objects` 全库扫描证实）。

**后果**：造成**可复现性断点**。报告里「两脚本口径一致」这一条只对旧版脚本成立；
新版脚本加了费用科目后，同一命令的结果从 `0.30元 / 0.020%` 变成 `0.48元 / 0.032%`。

**可复用规则**：
> **送审前必须先 commit 被审版本，并在审查期间冻结它。**
> "边审边改"会让审查结论失去锚点，审查员的算术复核可能指向一个已不存在的对象。

作者的处理方式是：把这件事本身当作**流程失败**记入复盘，而不是解释成"影响有限"。

## 五、审查的组织方式（多智能体）

### 5.1 分派与并行

- **互不依赖的取证线同一条消息发出**（例如「市场数据 / 规则费用 / 对抗审查」三路并行），不串行搜
- **关键收益**：某次并行中，规则核查线上的一手发现（监管机构正在调研某项费率存废）
  **直接改变了方案的战略重心** —— 串行做的话，方案会按错前提设计完 8 份交付物

### 5.2 分层审查

跨任务/跨文件的语义不一致，**只有全分支评审能抓**：

- 计划自身有 3 处缺陷，**预检扫描误判其中 2 处"已修复"** → 预检不可替代逐任务评审
- 某格式化函数接收了绝对时间戳，显示成 `496944:23:45`；
  **单任务各自自洽、跨任务才矛盾** → 逐任务 + 全分支双层评审是必要的

### 5.3 评审模型分档

按任务性质选模型档位，实测**抓到的问题与模型档位正相关**：
机械转写用轻量档、集成/语义类用中档、最终全分支评审用最强档。

### 5.4 派活的两个坑

| 坑 | 事实 | 规则 |
|---|---|---|
| 子代理不能再生子代理 | 子代理里调用分派返回 `depth 2 exceeds maxDepth 1` | 派活时要么不假设它能再分派，要么在任务书里写明「不可再分派，用并发抓取替代」 |
| 只盯"已启动"会漏掉静默失败 | 4 个并行评审里**合规评审首跑静默失败**（无产出、无说明），重派后成功 | **分派后必须盯产出落盘，不能只盯"已启动"** |

### 5.5 提交卫生

`git add -A` 把工作区里**已存在但未提交的、别人产生的改动**一并纳入。
处置：`git commit --amend` 改写提交信息，**明确披露哪部分不是自己产生的**。

> **规则**：`git add -A` 之前先 `git status` 看清工作区；带了别人的东西，必须在提交信息里说清。

## 六、一份可复制的审查清单

- [ ] 被审对象已 **commit 并冻结**，审查期间不改
- [ ] 审查员**不接触**实现者的推理过程
- [ ] 审查结论每条**必须带复现证据**（命令 / 文件行号 / 一手原文链接）
- [ ] 审查员提出的主张，**与自己的判断冲突时回一手原文裁决**，不投票
- [ ] 区分「入口层受控」与「判定层正确」——**架构保证要分层声称**
- [ ] 检查是否有**假绿测试**（测试名字声称的事，和它实际断言的事是否一致）
- [ ] 修复按 TDD：**先写能复现缺陷的红测试**，再改实现
- [ ] 修复后**全量回归**，不是只跑新增的那几条
- [ ] 首版错误结论**留档**，不删
- [ ] 审查过程本身的失败（如边审边改）**也记入复盘**

---

## 七、一句话总结

> 独立审查能显著提高产出质量，但**不能替代一手原文裁决**。
> 它找出过 4 个真错误，也提出过 1 个自己错了的主张 —— **这两件事同样重要，都要写进复盘。**
