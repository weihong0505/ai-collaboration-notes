# AI 协作方法论笔记

> **How to make AI-assisted work falsifiable.**
> 一个人 + 多个 AI 代理，怎么把模糊需求变成**可复现、可审计、敢下否定结论**的交付物。
>
> 来源：作者 **41 份项目复盘，约 44 万字符**的真实工作记录。
> 本文档库只收录**能迁移到别的项目**的规则 —— 不收录只在单一项目成立的结论。

## 这是在讲什么

不是"怎么用 AI 写代码"。2026 年那已经是门槛了。

这里讲的是**下一步**：当 AI 能写出看起来正确的代码、生成看起来很专业的文档、
给出看起来很具体的结论时，**你怎么知道它是对的？**

三条主线：

1. **让产出可证伪** —— 判定标准在结果之前冻结；失败数据留在报告里；安全声称标明覆盖哪一层
2. **让审查有对账压力** —— 独立审查员不接触实现思路；冲突时回一手原文裁决；审查员自己错了也要记下来
3. **让失败无法静默** —— 每一类曾经出过错的地方，配一个能自动跑的检查

## 三条最能代表这套方法论的东西

### 一 · 判定线必须在看到结果之前冻结

某因子检验项目把判定阈值先写进配置文件入库，之后不回改。
结果：**4 个核心因子全部未过闸门**，报告里专门写了一节「未做选择性报告」。

> 在结果出来之后调整门槛，等于没有门槛。

### 二 · 审查员也会错，而且错法有规律

一份 842 行的独立审查报告，**找出 4 个真错误，同时提出 1 个它自己错了的主张**。
处置方式不是投票、也不是取"看起来更细"的一方 —— 而是回一手原文取三份文件裁决，
判定它属**「表种错配」**（用了一张本不该包含该费用的表，去证明该费用不存在）。

> **「看起来更具体」≠「更正确」。** 细节密度会造成可信度错觉。

### 三 · 失败数据比成功数据更有说服力

- 一个基准表里保留着「189 ms（历史值，**现不可复现**）」那一行，**没删**
- 一个回测报告单列一节「首版错误结论留档（备审计）」，写明根因与修正值
- 被淘汰的因子，其页面记录的是**淘汰过程**，不是用法

> 一个只展示成功数据的项目，读者无法判断作者有没有分辨能力。

## 一条贯穿全部案例的规律

> **「命令成功返回 / 退出码 0 / 测试全绿」不等于「结果正确」。**

这个等式在**三个技术栈完全不同的项目**（前端小程序 / Python 教学 / 系统安装）
里各被真实事故证伪过一次以上。实际发生过的例子：

| 看起来 | 实际是 |
|---|---|
| 测试全绿 | 依赖根本没真正注入，读写全丢 |
| 脚本报成功 | 批量替换把三份文档的字符改坏了，因为索引退化成了"第一个字符" |
| 页面无报错 | 画布选择器没匹配到节点，静默 return |
| 版本号正确 | 装的是 CPU 版，跑到某个算子才炸 |
| 进度条正常 | 非 ASCII 写入失败，工具返回 `{"ok": true}` |

## 取材范围

这些规则来自 10 个以上互不相关的技术栈上的真实工作，包括：
微信小程序 · Python/VLM 教学 · Linux 裸机安装 · 数学建模 · 量化因子检验与回测 ·
3D 角色动画重定向 · Web 安全审计 · 硬件推理基准 · 桌面 GUI 自动化 · 软件著作权合规评估。

**方法论不随项目类型漂移** —— 「先验证再声称、只留一个源、改动可回退、错误路径也要测」
这四条在三个完全不同的领域里各自被真实事故验证过。

## 边界（先说清楚）

- **这是工作留痕的提炼，不是教程。** 很多地方假设你知道什么是 IC、ECE、段错误、FTS5。
- **有失败没写进来。** 只有"被自己或审查发现、并留下了可复用规则"的那些才收录。
- **不是科研结论。** 这些是单人在实际项目里验证过的工程纪律，样本是 1 个人、41 个项目。
- **没有一处是虚构的。** 每个案例、每个数字、每个文件名都能在原始复盘里定位到。
